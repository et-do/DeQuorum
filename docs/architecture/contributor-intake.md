# Contributor Intake — Design

> **Status:** canonical design for v0.2 → v1.0 contributor intake. Today's CLI / web submit form is the simplest possible thing that satisfies the v0.1 row of the phased plan in §11.

## 1. What kind of system this is

Mental model: **Wikipedia's editing rigor × GitHub's PR / version-control discipline × Stack Overflow's voting × DOI-style permanent citations**. None of those existing systems individually fits — we need their union.

What makes DeQuorum's version different from any of them:
- Every claim is **cryptographically signed** by its contributor; provenance is enforced by the protocol, not by social trust.
- **Voting decides truth.** There is no editor-in-chief, no admin override, no centralized authority.
- **Kickbacks** create real economic incentive for both contribution quality and review effort.
- **Federation-first**: the design must work when 10+ instances mirror each other.

Two implications that fall out of those constraints, that we hold throughout the rest of this doc:

1. **The contributor is always in the loop for what gets signed in their name.** No silent LLM-extraction that becomes their signed claim.
2. **Sybil resistance comes from the cost of *influence*, not from blocking entry.** Anyone can sign up. What climbs is what your vote weighs and what you can submit at scale.

## 2. Identity & Sybil resistance (the layered defense)

Five tiers. Higher tiers cost more to reach, but the network keeps working with people at every level.

| Tier | What you've proved | What you can do | Vote weight | Submission limit |
| --- | --- | --- | --- | --- |
| **0** | nothing (anonymous) | read | 0 | — |
| **1** | working email | submit contributions, see review queue | 0 (votes recorded but ignored) | 5/day |
| **2** | one connected social proof (signed claim from a GitHub / Twitter / personal domain that the network can verify) | full voting, can earn reviewer status | 1.0× | 50/day |
| **3** | W3C Verifiable Credential **OR** sustained reputation in a category | full voting + weighted in matching domain + can submit on behalf of an org | 2-5× in matching domain | 500/day |
| **4** | curator nomination ratified by other reviewers in the same category | issue category-scoped overrides / vetoes; cap ~5-15 curators per category | 1.0× (same as tier 2 in voting; the privilege is veto, not weight) | unlimited |

How each tier check works concretely:

- **Tier 1**: standard email verification link, kept simple. Used to slow but not stop bot floods.
- **Tier 2**: contributor posts a signed text snippet (auto-generated by the network) at a profile URL they control. A cron-style worker fetches the URL, verifies the signature against their public key, and grants Tier 2 once verified. Decent attack-cost-vs-friction ratio for individuals; orgs use Tier 3.
- **Tier 3 (credential path)**: W3C VC + DID resolution + issuer trust check. The network keeps an issuer-trust list voted on by curators. Adding a new issuer (e.g. a new medical board) goes through curator vote.
- **Tier 3 (reputation path)**: ≥X votes cast in a category over Y months with a consensus-match rate ≥Z% earns Tier 3 in that category. Tunable thresholds; expect ~6-12 months of active voting for a fresh account.
- **Tier 4**: nominated by ≥3 existing curators in the same category, ratified by a vote of the existing reviewers. Caps deliberately small so it stays meaningful.

Plus, baseline defenses that apply at all tiers:
- Every vote / submission is **signed**; every signer's history is **visible**. Coordinated brigading is detectable in retrospect.
- **Rate limits per tier** (the right column above).
- **Vote-pattern audit tooling**: surface tightly-correlated voter clusters for curator review. Doesn't auto-act; flags for humans.

Notable: **none of these tiers are credentials**. A doctor doesn't get a special "MD" account. They just have a verified credential attached to their otherwise-equal Tier 2 account, which boosts their vote weight in medical categories.

## 3. Onboarding flow

UX commitments:
- "I want to contribute" → first submission in **under 5 minutes**.
- Tier 1 is the default after signup.
- No required credentials, ever.
- Agreement is short, plain English, versioned, and re-signed when the version bumps.
- Keypair generated client-side (we never touch the private key).

The flow:

```
1. /onboarding (single page)
   - Display name
   - Email (verified async)
   - WebCrypto generates Ed25519 keypair
        -> private key stored in browser IndexedDB
        -> downloadable backup file shown ONCE
   - Agreement v1.x shown -> signed by their new key
   - Optional: bio, social proof links, credentials

2. Account becomes active at Tier 1 the moment email verifies.

3. /onboarding/upgrade (later)
   - Submit social proof or credentials any time
   - Tier auto-promotes on verification
```

API endpoints supporting this:
- `POST /contributors` — accepts (display_name, public_key, agreement_signature, email)
- `POST /contributors/:id/verify-email/:token`
- `POST /contributors/:id/social-proof` (initiates Tier 2 verification)
- `POST /contributors/:id/credentials` (registers a W3C VC for Tier 3)

## 4. Categories & Lexicon

**Hybrid taxonomy + folksonomy.** Pure folksonomy gives Stack-Overflow-style tag soup at scale; pure taxonomy ossifies and excludes new domains. We commit to both:

### Curated top-level categories

~30 top-level categories at launch. Hierarchy goes 2-3 levels deep, curated. The seed tree (illustrative, not final):

```
Programming
  Python · typing · async · packaging · ...
  Rust · ownership · async · ...
  JavaScript · TypeScript · Node · browser · ...
  Go · ...
Science
  Biology · cell · genetics · evolution · ...
  Chemistry · organic · physical · ...
  Physics · classical · quantum · ...
Mathematics
  Pure · Applied · Statistics · ...
Humanities
  History · Linguistics · Philosophy · ...
Health
  Anatomy · Nutrition · Mental health · ...
Crafts & how-to
  Cooking · Woodworking · Gardening · ...
Law (general; jurisdiction-specific tags below)
Finance & economics
... (~30 top-level)
```

Adding a new top-level category requires:
- Proposal by a Tier 2+ contributor with rationale
- Vote by ≥5 Tier 3 reviewers across existing categories
- Auto-merge if approved

### Free tags (folksonomy)

Every contribution carries up to ~10 free tags in addition to its primary category. Tags adapt to how the contributor community actually talks. Examples on a Python typing contribution: `pep612`, `paramspec`, `decorator`, `forwarding`.

Tag merge / rename happens via voting too — a curator in the category can propose "merge `paramspec` into `param-spec`" and reviewers vote.

### What categories drive

| Function | How the category matters |
| --- | --- |
| Routing | Embedding router uses category + tags as part of the category profile text |
| Reputation | Earned per-category, not globally |
| Browsing & discovery | Category tree is the navigation |
| Sponsored verticals | A sponsor sponsors a category subtree |
| Vote weighting | Tier 3 weight only applies in matching category |

## 5. Submission UX (single claim)

The simplest path — for someone who just wants to add one fact:

```
Step 1: paste the claim text
        -> as you type, the form runs duplicate detection (§6a) in the background
Step 2: pick a category (autocompleted suggestion based on text)
Step 3: add citation URLs (at least one required)
Step 4: add free tags (optional, suggested)
Submit
```

Progressive disclosure: a contributor who just wants to submit one fact never sees document upload, bulk extraction, version controls, etc. Those are revealed only when they're useful.

## 6. Quality gates *before* the review queue

Three checks run automatically on submit. The bias is: **surface, don't reject**. We want to inform contributors, not gate them out, unless something is unambiguously broken.

### 6a. Duplicate detection (similarity search)

The single most important quality gate. Without it the store fills with paraphrases of the same claim.

```
1. Embed the new claim with sentence-transformers
2. Cosine-similarity vs every approved contribution in same category
3. Surface result by band:
   - >0.90: "Very likely duplicate of X. Open it to update / extend instead?"
   - 0.70-0.90: "Related to X. Proceed if your claim is distinct."
   - <0.70: clear, no prompt
```

Final call is the contributor's. If they proceed past a >0.90 warning, the review queue sees both the new submission *and* the high-similarity neighbor side-by-side so voters can judge whether to approve or reject as duplicate.

### 6b. Schema gates (hard reject)

- Claim text 50–1500 chars
- At least one citation URL, HTTPS only
- Citation URLs respond to a HEAD request within 5s
- Category required
- Plain text, no executable code
- ≤10 tags

Failing any of these blocks submission with a clear error.

### 6c. Content filters (hard reject for some, soft signal for others)

| Check | Action |
| --- | --- |
| Known harmful-content patterns (CSAM signatures, doxxing patterns) | hard reject + flag for curator review |
| PII detection (regex + NER) | warn contributor; require acknowledgement |
| LLM-assisted "does this read as a factual claim?" | soft signal added to review queue notes; doesn't block |

Soft signals do not change vote outcomes — they're context for voters.

## 7. Review & approval (with delegation)

The vote mechanism is the existing one. What evolves is **who counts and by how much**.

### Reputation accumulation

Per-category. Two inputs:

1. **Vote-consensus match.** When you vote, your reputation in that category moves based on whether your vote matched the eventual approval/rejection outcome. Match → +small. Mismatch → -small.
2. **Submission outcomes.** Contributions you submit that get approved → +medium boost. Rejected → -small.

Reputation decays slowly (half-life ~6 months) so it reflects current activity, not legacy.

### Vote weighting

The default vote weight today is 1. The evolved version:

| Voter status | Weight |
| --- | --- |
| Tier 1 (email only) | 0 — recorded but not counted |
| Tier 2, no domain reputation | 1.0× |
| Tier 2, has Tier 3 by reputation in category | 2.5× |
| Tier 3 by credential in matching category | 3.0× (and credential type shown as a badge) |
| Reviewer (top 10% by category reputation) | additional fast-track power, see below |
| Curator | 1.0× weight; the privilege is veto, not weight |

### Approval delegation — fast-track and veto

Vanilla rule today: +2 net score = approved. We keep that as the default.

**Fast-track** (saves time on obvious approvals): if one Reviewer + one regular Tier 2 both vote +1 on the same contribution, it becomes approved without a second regular vote. Reviewer status is earned, not assigned — top 10% by reputation in the relevant category.

**Curator override**: a Curator (Tier 4 in same category) can:
- Issue an instant-approve override (signed, visible) for a Tier 3-flagged claim if it's clearly correct and time-sensitive (e.g. retracted-paper correction).
- Issue an instant-reject override for unambiguous abuse (CSAM, doxxing).

All overrides are publicly logged; an override decision can itself be challenged via the regular vote queue, and consistent override misuse costs the curator their status via reviewer vote.

This is the "approval control status" you asked about. It's a **rank, not a role**: nobody is appointed; you climb because the network's voting history says so.

## 8. Versioning approved content

Live content needs updates. We treat every contribution as one entry in a versioned **lineage**.

### Model

```
Contribution (extended)
  contribution_id     — content-hash of this specific version
  lineage_id          — stable across all versions of "this claim"
  version_number      — 1, 2, 3, ...
  parent_version      — the version this edit branched from (or null)
  status              — pending | approved | rejected | superseded
```

A contributor can open any approved contribution, edit text or citations, and submit the result. That creates a new contribution in the same lineage with `version_number = parent + 1` and `status = pending`. It goes through the review queue with a diff view shown to voters. On approval: previous version becomes `superseded`, new version is the "current" of the lineage. On rejection: previous version stays current; rejected version is preserved for audit but doesn't appear in retrieval.

### Citations

Every citation refers to a `lineage_id`, not a `contribution_id`. Two retrieval semantics:

- **Auto-follow** (default): the citation always resolves to the current approved version of the lineage. Useful for "the latest understanding of X."
- **Pinned**: the citation specifies `lineage:abc123@v2`, locking to that version. Useful for academic-style audit trails ("what we believed when we wrote this paper").

Both are first-class. The submission UI lets the citing contributor pick.

### Superseded versions

Stay in the store. Indexed. Searchable by audit tools. Just don't surface in retrieval. This is the "version control" you asked about: history isn't deleted, just shelved.

## 9. Git-controlled / power-user submission lane

Some contributors — OSS maintainers especially — will want git-style ergonomics. **The semantics of every submission are already git-like** (versioned, signed, reviewable, diffable). We expose a CLI lane that mirrors that:

```bash
# Generate a proposal from a local file
dequorum contribute --from-file claims.md --category programming/python/typing

# Or update existing
dequorum update --lineage abc123 --diff-from claims.md

# Or submit via JSON
dequorum submit-batch < proposals.json
```

Underneath: produces the same signed `Contribution` records that the web form produces. Same review queue, same vote mechanism, same outcomes.

For maintainers used to GitHub PR review: we ship a `dequorum review --lineage abc123` command that shows the proposed diff, lets them cast a signed vote with a comment, and that's it.

**There is no separate "git backend."** The version control semantics are intrinsic to the data model. The git CLI is just a friendly surface for power users; nothing in security or quality depends on which surface a contributor uses.

## 10. Bulk document submission (revised)

When a contributor uploads `mypaper.md` (or pastes a long article, or provides a URL):

```
Upload (paste / file / URL)
  -> Document content fetched, signed by contributor, stored
  -> Extract proposed claims:
        (a) sentence-segment + filter for declarative sentences
        (b) LLM-assisted: "rewrite each paragraph as N standalone claims with citations"
  -> Per proposed claim:
        (i)   suggest 1-3 candidate categories (embedding match)
        (ii)  run duplicate detection (§6a)
        (iii) present to contributor in a review UI with edit/skip/approve
  -> Contributor confirms per-claim (or bulk-confirms with one click)
  -> Each confirmed claim becomes a signed Contribution(status=pending), linked
     back to (document_id, byte_span) via contribution_sources table
  -> Enters review queue normally
```

The Document itself can be reviewable too (a "is this source reliable?" vote) for high-stakes domains. For most domains it isn't necessary — the per-claim vote does the work.

**Key principle (restated):** the contributor approves every claim before it gets signed in their name. The LLM is a proposal-maker, not a content-signer.

## 11. Phased rollout

| Phase | Ships | Triggers when |
| --- | --- | --- |
| **v0.1 (today)** | Single-claim CLI/web, hardcoded keys, default voting | already shipped |
| **v0.2** | Contributor entity + signup + agreement + email Tier 1 + social-proof Tier 2 | first external testers |
| **v0.3** | Curated top-level categories + duplicate detection on submit | ~50 contributions per category in seed data |
| **v0.4** | Reputation accumulation + reviewer fast-track + vote-pattern audit | once ~50 voters active |
| **v0.5** | Lineage / versioning model + update workflow + diff review UI | when first approved contributions need updates |
| **v0.6** | Paste-text bulk extract + per-claim confirm | as soon as a contributor wants to submit >1 fact |
| **v0.7** | File upload (.md, .txt) + URL fetch + PDF text extraction | with momentum behind v0.6 |
| **v0.8** | Curator nomination flow + Tier 4 vetoes | when the first category gets dense enough to need curators |
| **v0.9** | W3C VC + Tier 3 credential weighting | when we hit a domain that needs it (medical / legal) |
| **v1.0** | Federation: cross-instance signed lineages | when 2+ instances exist |

This is the order in which capabilities become *load-bearing*, not the order in which they must be built. Some can happen in parallel.

## 12. Data model deltas (cross-ref [services/db/data-model.dbml](../../services/db/data-model.dbml))

Already in the DBML:
- `contributors`, `credentials`, `documents`, `contribution_sources`, `reputation`, `ledger_entries`

New tables this doc adds:
- `categories` — the curated taxonomy. `(category_id, parent_id, slug, display_name, description, created_at)`
- `contribution_categories` — many-to-many between contributions and categories. (A contribution has exactly one *primary* category and may have several secondary.)
- `contribution_tags` — many-to-many for free tags. `(contribution_id, tag_slug)`.
- `agreements` — versioned TOS texts. `(version, text, hash, effective_at)`. Contributors' signatures reference a version row.
- `contribution_lineages` — for versioning. `(lineage_id, created_at, current_contribution_id)`.
- `tier_assignments` — per-contributor tier + reason audit. `(contributor_id, tier, granted_at, granted_by_method)`.

Existing tables that change shape:
- `contributions`: add `lineage_id`, `version_number`, `parent_version`, `primary_category_id`. The `contribution_id` content-hash now includes `(version_number, parent_version)` so each version is content-unique.
- `votes`: add `weight` (the weight at the time of the vote, frozen) so audit can reconstruct how a tally was reached.

I'll update [services/db/data-model.dbml](../../services/db/data-model.dbml) in the same PR that lands v0.2 — until then, the DBML and this doc agree on the existing tables and disagree on the new ones, which is fine for a forward-looking spec.

## 13. Open questions to revisit at build time

- **Granularity of LLM-assisted extraction.** One claim per sentence over-fragments; one per paragraph is too coarse. Empirical.
- **Cross-language deduplication.** "Asyncio is the standard Python async library" in English and the same claim in Spanish are arguably duplicates. Cross-language embeddings exist; whether to merge or keep parallel is policy.
- **Coordinated reviewer collusion.** A clique of high-rep reviewers in a category can rubber-stamp each other. Audit tooling can detect; the policy response is open. Probably: surface clusters → curator review → consequences range from reputation reset to category split.
- **DMCA / takedown.** Some kind of legal escalation path. Document-level rather than contribution-level probably. Defer to v0.7+.
- **Credential issuer trust list governance.** Adding a new issuer (e.g. a new medical board) needs a process. Curator vote, probably.
- **Reputation decay rate.** Half-life of 6 months is a guess. Tune empirically once active.
- **LLM extraction trust.** We use a model to extract claims that another model will later use. Compounding errors are real. Mitigation: the contributor reviewing each claim before signing is the key defense, but we should also instrument extraction confidence and track.

## 14. What this design protects against

A quick summary of the threats and how we address each:

| Threat | Defense |
| --- | --- |
| Bot submissions flooding the queue | Tier 1 rate limit (5/day); duplicate detection; schema gates |
| Sybil voting (one person, many accounts) | Tier ladder; vote-pattern audit; reputation per-category not transferable across accounts |
| Vote brigading (coordinated push to approve garbage) | Audit tools; curator veto; reputation rep cost when consensus rejects approved-by-brigade item later |
| Subtle low-quality "looks ok" claims | Duplicate detection surfaces existing better versions; vote weight gives experienced reviewers more influence; soft LLM signal in queue notes |
| Garbage uploaded as "public domain" when it isn't | Agreement attestation (puts liability on contributor per DMCA safe-harbor pattern); takedown path |
| Approved content becoming outdated | Versioning + lineage + update workflow; auto-follow citations track current |
| Stale categories | Category proposals / merges go through reviewer vote |
| Wrong category routing | Embedding router + KeywordRouter fallback (already shipped); category restricts the candidate pool |
| Single-instance lock-in | Federation in v1.0; signed lineages are portable; reputation per-instance (so no one instance can ban-effectively-globally) |

## 15. What this design depends on (assumptions to validate)

- Contributors will tolerate a 5-minute signup with email verification before their first submission. (Likely true based on every comparable platform.)
- Duplicate detection at ~80% recall is enough to keep the store usable. (Empirically testable on real data.)
- Reputation-weighted voting is fair enough that newcomers feel they can earn influence. (Hardest to validate; needs alpha testers.)
- The curator role doesn't accidentally become an oligarchy. (Caps + reviewer-vote-out path are the structural defense; should be revisited post-launch.)
- The LLM-assisted extraction is good enough that contributors mostly approve proposed claims rather than rejecting half. (Empirical; if the model is bad at this we fall back to manual segmentation.)
